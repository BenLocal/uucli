# Zig 运行时踩坑

> Zig 0.17 程序在不同平台上跑起来才暴露的问题：线程、TLS、信号。

- 2026-11-16 Linux 上 `uucli term` 一启动就 panic `reached unreachable code`（ReleaseSafe 栈指向 `Thread.zig` 的 `pthread_detach`，Debug 下实为 `pthread_create` 返回 `EINVAL`）→ Zig 0.17.1 默认 `std.options.signal_stack_size = 1 << 18`，每个线程带一块 256 KiB 的 threadlocal 备用信号栈，glibc 把静态 TLS 放在线程栈里，`interrupts.zig` 用 `.stack_size = 64 * 1024` spawn 时装不下；macOS 的 TLS 不占线程栈所以从没出过问题 → 不要给 `std.Thread.spawn` 指定小于 TLS 的栈大小，用默认值（16 MiB 只是虚拟预留）。实测：最小复现程序 256 KiB 失败、512 KiB 通过；`readelf -lW <bin> | grep TLS` 看 TLS 大小。回归测试：`src/interrupts.zig` 的 "install starts the reader thread and delivers SIGTERM to the bus"。
- 2026-11-16 ReleaseSafe 版 `uucli term FAV` 在提示输入验证码后 `Illegal instruction`，panic 栈指向 `posix.tcgetattr` 的 `.NOTTY` 一行（又是错位）→ gdb 抓到真实位置是 `compiler_rt.ssp.__chk_fail`：`tcgetattr` 返回前栈金丝雀被改写。原因：Zig 0.17.1 在 glibc 下 `std.posix.termios` 是内核的 44 字节结构，glibc 的 `tcgetattr` 写 60 字节 `struct termios`，多写 16 字节；Debug 没有栈保护，只是悄悄写坏栈（`terminal` 的 raw 模式一直带着这个问题）→ Linux 上改用 `std.os.linux.tcgetattr/tcsetattr`（ioctl `TCGETS`/`TCSETS`，内核结构），见 `src/tty.zig` `getAttr`。实测：最小程序 `@sizeOf(std.posix.termios)` 44、C `sizeof(struct termios)` 60。ReleaseSafe 崩溃先用 `gdb -batch -ex run -ex bt` 看真实帧，别信 panic 栈；需要 TTY 时用 `script -qec "…" /dev/null`。
